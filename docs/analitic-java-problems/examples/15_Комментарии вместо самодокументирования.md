# Комментарии вместо самодокументирования

**Категория:** Стиль кодирования (Clean Code)

**Описание:** Код настолько запутан, что требует пояснений, которые дублируют логику.

**Инструменты:** PMD, Checkstyle

---

Вот пример, демонстрирующий проблему «Комментарии вместо самодокументирования» и её решение на Java.

---

### Корректный пример

Код написан так, что его назначение понятно из названий переменных, методов и логики без дополнительных пояснений.

```java
public class PriceCalculator {

    public double calculateTotalWithDiscount(double basePrice, int customerLoyaltyYears) {
        double discountRate = getDiscountRateByLoyalty(customerLoyaltyYears);
        double discountedPrice = basePrice * (1 - discountRate);
        double tax = discountedPrice * 0.2; // 20% налог (можно вынести в константу)
        return discountedPrice + tax;
    }

    private double getDiscountRateByLoyalty(int years) {
        if (years >= 5) {
            return 0.15; // 15% скидка для постоянных клиентов
        } else if (years >= 2) {
            return 0.10; // 10% скидка
        } else {
            return 0.0;
        }
    }
}
```

**Почему это корректно:**
- Названия методов и переменных говорят сами за себя (`customerLoyaltyYears`, `getDiscountRateByLoyalty`).
- Логика разбита на маленькие методы с понятными именами.
- Комментарии используются только для пояснения магических чисел (ставка налога, проценты скидки), что допустимо, но их тоже можно вынести в константы.

### Некорректный пример

Код содержит многословные комментарии, которые просто пересказывают то, что делает программа, вместо того чтобы сделать код понятным самому.

```java
public class PriceCalculator {

    // Этот метод вычисляет итоговую цену с учётом скидки и налога
    public double calculateTotalWithDiscount(double basePrice, int customerLoyaltyYears) {
        // Переменная для хранения скидки
        double d;
        // Если клиент с нами больше 5 лет
        if (customerLoyaltyYears >= 5) {
            // Присваиваем скидку 0.15 (15%)
            d = 0.15;
        } else {
            // Иначе если больше 2 лет
            if (customerLoyaltyYears >= 2) {
                // Присваиваем скидку 0.10 (10%)
                d = 0.10;
            } else {
                // Иначе скидка 0
                d = 0.0;
            }
        }
        // Вычисляем цену со скидкой: базовая цена * (1 - скидка)
        double p = basePrice * (1 - d);
        // Вычисляем налог 20% от цены со скидкой
        double t = p * 0.2;
        // Итоговая цена = цена со скидкой + налог
        double result = p + t;
        // Возвращаем результат
        return result;
    }
}
```

### Объяснение и выявление инструментом

**Почему этот код плох:**
1. **Избыточные комментарии** — каждый шаг дублируется в тексте, хотя код очевиден.
2. **Плохие имена переменных** — `d`, `p`, `t`, `result` ничего не говорят о своём назначении.
3. **Нарушение принципа самодокументирования** — вместо того чтобы сделать код читаемым, автор полагается на комментарии.
4. **Комментарии устаревают** — при изменении логики их часто забывают обновить, что приводит к дезинформации.

**Какой инструмент и какое правило сработает:**

- **PMD** — правило `CommentRequired` (в некоторых конфигурациях) или `TooManyComments` (если настроено). Также сработает `AvoidCommentingOutCode` (хотя здесь не закомментированный код, а избыточные комментарии). Более точно: правило `CommentDefaultAccessModifier` не подходит, но можно использовать кастомное правило или `CommentSize`.
- **Checkstyle** — правило `CommentsIndentation` не совсем про это. Но есть правило `JavadocMethod` (если комментарии оформлены как Javadoc, но не несут новой информации). Самое подходящее — **`CommentsIndentation`** косвенно, но основное — это **`UncommentedMain`** (не наш случай). Однако для данной проблемы лучше всего подходит **`AvoidInlineConditionals`** (не про комментарии). На практике в Checkstyle нет прямого правила «запретить комментарии, дублирующие код». Но можно использовать **`RegexpSingleline`** с шаблоном, запрещающим строки вида `// присваиваем`, `// вычисляем` и т.п.

**Рекомендация:** Для автоматического выявления таких проблем лучше всего использовать **PMD** с правилом **`CommentRequired`** (уровень `header` или `method`), настроив его так, чтобы он требовал осмысленные комментарии только для сложных участков, или использовать **Checkstyle** с кастомным регулярным выражением, например:
```xml
<module name="RegexpSingleline">
    <property name="format" value="// (присваиваем|вычисляем|возвращаем|переменная)"/>
    <property name="message" value="Избегайте комментариев, которые просто пересказывают код."/>
</module>
```

**Вывод:** Проблема обнаруживается статическим анализом, если настроить правила на выявление избыточных, тривиальных комментариев (например, через регулярные выражения в Checkstyle или кастомные правила PMD).
