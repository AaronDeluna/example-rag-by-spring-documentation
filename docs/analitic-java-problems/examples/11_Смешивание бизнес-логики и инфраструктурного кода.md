# Смешивание бизнес-логики и инфраструктурного кода

**Категория:** Архитектурные принципы (Чистая архитектура)

**Описание:** Например, прямое использование аннотаций фреймворка (Spring, JPA) в доменных классах.

**Инструменты:** DesigniteJava, PMD

---

Вот пример, демонстрирующий проблему смешивания бизнес-логики и инфраструктурного кода на Java, с корректным и некорректным подходами.

---

### Корректный пример

**Описание:**  
Доменный класс `Order` не содержит аннотаций Spring/JPA. Вся инфраструктура (маппинг в БД, DI) вынесена в отдельные классы. Бизнес-логика чистая и тестируемая.

```java
// Чистый доменный класс (POJO)
public class Order {
    private String id;
    private double amount;
    private boolean paid;

    public Order(String id, double amount) {
        this.id = id;
        this.amount = amount;
        this.paid = false;
    }

    // Бизнес-метод
    public void markAsPaid() {
        if (paid) {
            throw new IllegalStateException("Order already paid");
        }
        this.paid = true;
    }

    // Геттеры (без сеттеров — неизменяемость)
    public String getId() { return id; }
    public double getAmount() { return amount; }
    public boolean isPaid() { return paid; }
}

// Отдельный инфраструктурный класс для JPA
@Entity
@Table(name = "orders")
public class OrderEntity {
    @Id
    private String id;
    private double amount;
    private boolean paid;

    public OrderEntity() {} // для JPA

    public OrderEntity(Order order) {
        this.id = order.getId();
        this.amount = order.getAmount();
        this.paid = order.isPaid();
    }

    public Order toDomain() {
        return new Order(this.id, this.amount);
    }
}
```

**Почему хорошо:**  
- Доменный класс не зависит от фреймворков.  
- Легко тестировать `Order.markAsPaid()` без Spring.  
- Инфраструктура отделена (принцип инверсии зависимостей).

### Некорректный пример

**Описание:**  
Доменный класс `Order` напрямую использует аннотации JPA и Spring, что нарушает принципы чистой архитектуры.

```java
// Плохо: смешивание бизнес-логики и инфраструктуры
@Entity
@Table(name = "orders")
@Component  // Spring-аннотация в домене
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private String id;

    @Column(name = "amount")
    private double amount;

    @Column(name = "paid")
    private boolean paid;

    // Обязательный пустой конструктор для JPA
    public Order() {}

    public Order(String id, double amount) {
        this.id = id;
        this.amount = amount;
        this.paid = false;
    }

    // Бизнес-метод прямо в сущности
    public void markAsPaid() {
        if (paid) {
            throw new IllegalStateException("Order already paid");
        }
        this.paid = true;
    }

    // Геттеры/сеттеры (сеттеры для JPA — нарушение инкапсуляции)
    public void setPaid(boolean paid) { this.paid = paid; }
}
```

**Почему плохо:**  
1. **Нарушение чистой архитектуры:** Доменная модель зависит от JPA (`@Entity`, `@Id`, `@Column`) и Spring (`@Component`).  
2. **Сложность тестирования:** Для теста `markAsPaid()` придётся поднимать Spring-контекст или мокать JPA.  
3. **Снижение гибкости:** Смена фреймворка (например, с JPA на MyBatis) потребует переписывания домена.  
4. **Побочные эффекты:** Пустой конструктор и сеттеры — уступки JPA, которые могут привести к некорректным состояниям объекта.

---

### Объяснение и выявление инструментом

**Инструмент:** **DesigniteJava** (или **PMD** с правилом `DataClass` / `GodClass`).

**Как сработает:**  
- **DesigniteJava** анализирует зависимости классов. Правило **«Data Class»** (и более общее **«Architecture Violation»**) обнаружит, что класс `Order` одновременно содержит бизнес-методы (`markAsPaid`) и аннотации инфраструктуры (`@Entity`, `@Component`).  
- **PMD** с правилом **`TooManyFields`** или **`ExcessivePublicCount`** может косвенно указать на излишнюю ответственность класса. Однако для прямого выявления смешивания логики и инфраструктуры лучше использовать **DesigniteJava**, так как он специализируется на архитектурных дефектах.

**Пример вывода DesigniteJava:**  
```
Class: Order
- Violation: Mixed Responsibility (Business Logic + Infrastructure Annotations)
- Severity: High
- Description: Domain class contains both business methods and JPA/Spring annotations. Consider separating into domain entity and persistence entity.
```

**Дополнительно:**  
- **PMD** с правилом **`EntityModel`** (если включён) может предупредить о наличии бизнес-логики в JPA-сущности.  
- **IntelliJ IDEA** (встроенный инспектор) также подсветит смешивание, если включены проверки архитектуры.

**Итог:**  
Некорректный код нарушает принцип единственной ответственности (SRP) и чистую архитектуру. Инструмент **DesigniteJava** явно укажет на это через правило «Mixed Responsibility».
