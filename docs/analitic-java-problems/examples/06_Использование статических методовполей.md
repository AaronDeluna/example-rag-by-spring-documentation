# Использование статических методов/полей

**Категория:** Архитектурные принципы (Design for Testability)

**Описание:** Затрудняет мокирование и изоляцию при тестировании.

**Инструменты:** DesigniteJava, PMD

---

Вот пример, демонстрирующий проблему использования статических методов/полей и способы её решения, с указанием инструментов статического анализа.

---

### Корректный пример

**Идея:** Класс `PaymentService` использует внешний сервис для валидации платежей. Вместо статического метода используется интерфейс и внедрение зависимости (Dependency Injection), что позволяет легко подменить реализацию в тестах.

```java
// Интерфейс для внешнего сервиса
interface PaymentValidator {
    boolean validate(String cardNumber);
}

// Реализация, работающая с реальным API
class RealPaymentValidator implements PaymentValidator {
    @Override
    public boolean validate(String cardNumber) {
        // Логика обращения к внешнему API
        return cardNumber.startsWith("4"); // Упрощённая проверка
    }
}

// Класс, использующий внедрение зависимости
class PaymentService {
    private final PaymentValidator validator;

    // Зависимость передаётся через конструктор (Dependency Injection)
    public PaymentService(PaymentValidator validator) {
        this.validator = validator;
    }

    public void processPayment(String cardNumber) {
        if (!validator.validate(cardNumber)) {
            throw new IllegalArgumentException("Invalid card");
        }
        // Логика обработки платежа
    }
}

// Тест с мокированием (используя Mockito)
class PaymentServiceTest {
    @Test
    void testPaymentWithInvalidCard() {
        // Создаём мок вместо реального валидатора
        PaymentValidator mockValidator = mock(PaymentValidator.class);
        when(mockValidator.validate(anyString())).thenReturn(false);

        PaymentService service = new PaymentService(mockValidator);

        assertThrows(IllegalArgumentException.class, 
                     () -> service.processPayment("1234"));
    }
}
```

**Почему это корректно:**
- Легко мокировать: достаточно подменить реализацию `PaymentValidator`.
- Нет скрытых зависимостей: все внешние компоненты явно передаются в конструктор.
- Тестируемость: можно протестировать `PaymentService` без вызова реального API.

### Некорректный пример

**Идея:** Тот же функционал, но реализованный через статический метод. Класс `PaymentService` напрямую вызывает статический метод `PaymentValidator.validate()`.

```java
class PaymentValidator {
    // Статический метод — проблема для тестирования
    public static boolean validate(String cardNumber) {
        // Реальная логика, например, HTTP-запрос
        return cardNumber.startsWith("4");
    }
}

class PaymentService {
    public void processPayment(String cardNumber) {
        // Прямой вызов статического метода
        if (!PaymentValidator.validate(cardNumber)) {
            throw new IllegalArgumentException("Invalid card");
        }
        // Логика обработки платежа
    }
}

// Тест — невозможно изолировать PaymentService без вызова реального API
class PaymentServiceTest {
    @Test
    void testPaymentWithInvalidCard() {
        PaymentService service = new PaymentService();
        // Всегда будет вызываться реальный PaymentValidator.validate()
        // Нельзя подменить его поведение (если не использовать PowerMock)
        assertThrows(IllegalArgumentException.class, 
                     () -> service.processPayment("1234"));
    }
}
```

---

### Объяснение и выявление инструментом

**Почему некорректный пример плох:**
1. **Нарушение принципа инверсии зависимостей (DIP):** `PaymentService` жёстко привязан к конкретной реализации `PaymentValidator`.
2. **Невозможность мокирования:** Статические методы в Java не могут быть переопределены в наследниках, и стандартные фреймворки (Mockito, EasyMock) не могут их подменить без специальных расширений (например, PowerMock).
3. **Сложность тестирования:** Для тестирования `processPayment()` с некорректным номером карты придётся либо вызывать реальный API, либо использовать сложные и медленные инструменты (PowerMock, JMockit).
4. **Скрытые зависимости:** Разработчик, читающий код, не видит, что `PaymentService` зависит от внешнего сервиса, пока не заглянет в реализацию `processPayment()`.

**Какой инструмент и как выявит проблему:**

- **PMD** — правило `MethodReturnsInternalArray` не подходит, но есть правило **`TooManyStaticImports`** (косвенно), а главное — **`AvoidUsingStaticField`** и **`AvoidUsingStaticMethod`** (для архитектурных проверок).
  - В PMD есть категория **`design`** с правилом **`UseObjectForClearerAPI`** (рекомендует заменять статические методы на объектные).
  - Также можно использовать **`LawOfDemeter`** (проверяет, что класс не обращается к статическим методам других классов напрямую).
  
- **DesigniteJava** — специализированный инструмент для поиска архитектурных проблем. Он обнаружит:
  - **Static Method Access** — если класс `PaymentService` вызывает статический метод другого класса (`PaymentValidator.validate()`).
  - **Tight Coupling** — высокая связанность, так как `PaymentService` жёстко зависит от `PaymentValidator`.
  - **Testability Issue** — инструмент прямо укажет, что статический вызов снижает тестируемость.

**Пример срабатывания PMD:**
Если запустить PMD с правилом `java-design` (включающим `UseObjectForClearerAPI`), на строке `PaymentValidator.validate(cardNumber)` будет выдано предупреждение:
> "Avoid using static methods; prefer instance methods for better testability."

**Пример срабатывания DesigniteJava:**
В отчёте появится запись:
> **Issue:** Static method call in `PaymentService.processPayment()`  
> **Impact:** Low testability — cannot mock `PaymentValidator.validate()`  
> **Suggestion:** Use dependency injection and interface.

---

### Итог

| Критерий | Корректный пример | Некорректный пример |
|----------|-------------------|---------------------|
| Тестируемость | Высокая (мокирование) | Низкая (только PowerMock) |
| Связанность | Низкая (через интерфейс) | Высокая (статическая привязка) |
| Инструменты | Не вызовут предупреждений | PMD, DesigniteJava укажут на проблему |

Используйте объектные зависимости вместо статических методов — это сделает код гибким, тестируемым и поддерживаемым.
