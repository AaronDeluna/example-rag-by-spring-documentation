# Синглтоны и глобальные состояния

**Категория:** Архитектурные принципы (Design for Testability)

**Описание:** Тесты начинают влиять друг на друга из-за общего изменяемого состояния.

**Инструменты:** DesigniteJava, PMD

---

Вот примеры для проблемы «Синглтоны и глобальные состояния» с акцентом на взаимное влияние тестов.

---

### Корректный пример

**Идея:** Вместо глобального синглтона используем внедрение зависимости (Dependency Injection). Каждый тест создаёт свой экземпляр сервиса с чистым состоянием.

```java
// --- Класс, управляющий конфигурацией (без синглтона) ---
public class ConfigurationService {
    private String theme;

    public ConfigurationService() {
        this.theme = "light"; // состояние по умолчанию
    }

    public void setTheme(String theme) {
        this.theme = theme;
    }

    public String getTheme() {
        return theme;
    }
}

// --- Тест (JUnit 5) ---
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class ConfigurationServiceTest {

    @Test
    void testDefaultTheme() {
        // Каждый тест создаёт новый экземпляр — нет общего состояния
        ConfigurationService service = new ConfigurationService();
        assertEquals("light", service.getTheme());
    }

    @Test
    void testDarkTheme() {
        ConfigurationService service = new ConfigurationService();
        service.setTheme("dark");
        assertEquals("dark", service.getTheme());
    }
}
```

**Почему корректно:**
- Нет глобальной переменной или синглтона.
- Состояние изолировано в рамках одного теста.
- Тесты можно запускать в любом порядке — они не влияют друг на друга.

### Некорректный пример

**Идея:** Классический синглтон с изменяемым состоянием, который используется в тестах. Один тест меняет состояние, а другой от этого ломается.

```java
// --- Синглтон с глобальным состоянием ---
public class GlobalConfig {
    private static GlobalConfig instance = null;
    private String theme = "light";

    private GlobalConfig() {}

    public static GlobalConfig getInstance() {
        if (instance == null) {
            instance = new GlobalConfig();
        }
        return instance;
    }

    public void setTheme(String theme) {
        this.theme = theme;
    }

    public String getTheme() {
        return theme;
    }
}

// --- Тест, который страдает от проблемы ---
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

public class GlobalConfigTest {

    @Test
    void testDefaultTheme() {
        // Предполагаем, что никто не менял тему
        assertEquals("light", GlobalConfig.getInstance().getTheme());
    }

    @Test
    void testDarkTheme() {
        GlobalConfig.getInstance().setTheme("dark");
        assertEquals("dark", GlobalConfig.getInstance().getTheme());
    }
}
```

**Проблема:**  
Если тест `testDarkTheme` запустить раньше `testDefaultTheme`, то второй тест упадёт — он ожидает `"light"`, а получит `"dark"`, потому что синглтон сохранил изменение.

### Объяснение и выявление инструментом

**Почему плохо:**
- Синглтон хранит глобальное изменяемое состояние.
- Тесты теряют изоляцию — порядок выполнения влияет на результат.
- Нарушается принцип **Design for Testability**: код сложно тестировать независимо.

**Какой инструмент обнаружит:**
- **DesigniteJava** – может обнаружить использование синглтона с изменяемыми полями (rule: `Singleton with mutable state`).
- **PMD** – правило `SingularField` (если поле синглтона изменяется) или `AvoidSynchronizedAtMethodLevel` (в контексте неправильного управления состоянием).  
  Наиболее точное правило в PMD: **`NonThreadSafeSingleton`** – хотя оно в первую очередь про потокобезопасность, но часто срабатывает на изменяемых синглтонах, так как предполагает, что состояние может быть испорчено.

**Как именно сработает (на примере PMD):**
- PMD проанализирует класс `GlobalConfig` и увидит, что `instance` – статическое поле, а метод `getInstance()` не синхронизирован и возвращает изменяемый объект с публичными сеттерами.  
- Он выдаст предупреждение:  
  `"NonThreadSafeSingleton: Singleton is not thread safe"` – это косвенно укажет на проблему общего изменяемого состояния, которое опасно не только для многопоточности, но и для тестов.

**Вывод:**  
Чтобы избежать проблемы, всегда используйте **внедрение зависимостей** (через конструктор или параметры) вместо глобальных синглтонов с состоянием. Для тестов создавайте свежие экземпляры в каждом тесте.
