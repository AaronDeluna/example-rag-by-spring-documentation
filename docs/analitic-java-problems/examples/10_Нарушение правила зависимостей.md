# Нарушение правила зависимостей

**Категория:** Архитектурные принципы (Чистая архитектура)

**Описание:** Зависимости направлены от бизнес-логики к инфраструктуре, а не наоборот.

**Инструменты:** DesigniteJava, PMD

---

Вот пример, демонстрирующий нарушение правила зависимостей (Dependency Inversion Principle) в контексте Чистой архитектуры, когда бизнес-логика напрямую зависит от инфраструктуры, а не от абстракций.

---

### Корректный пример

В этом примере бизнес-логика (сервис) зависит только от абстракции (интерфейса), а инфраструктура реализует этот интерфейс. Таким образом, зависимости направлены внутрь — к абстракциям.

```java
// Абстракция (принадлежит слою бизнес-логики)
interface UserRepository {
    User findById(String userId);
}

// Бизнес-логика (слой use cases / domain)
class UserService {
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public String getUserEmail(String userId) {
        User user = userRepository.findById(userId);
        return user.getEmail();
    }
}

// Инфраструктура (реализация абстракции)
class DatabaseUserRepository implements UserRepository {
    @Override
    public User findById(String userId) {
        // Реальная работа с БД
        return new User(userId, "user@example.com");
    }
}

// Простая модель (тоже может быть в слое domain)
class User {
    private final String id;
    private final String email;

    public User(String id, String email) {
        this.id = id;
        this.email = email;
    }

    public String getEmail() {
        return email;
    }
}
```

**Почему это корректно:**  
- `UserService` (бизнес-логика) не знает о `DatabaseUserRepository` (инфраструктура).  
- Зависимость направлена от конкретной реализации к абстракции, а не наоборот.  
- Легко подменить реализацию (например, для тестов).

---

### Некорректный пример

Здесь бизнес-логика напрямую создаёт и использует конкретный класс инфраструктуры, нарушая принцип инверсии зависимостей.

```java
// Инфраструктура (конкретная реализация)
class DatabaseUserRepository {
    public User findById(String userId) {
        // Реальная работа с БД
        return new User(userId, "user@example.com");
    }
}

// Бизнес-логика (нарушает правило зависимостей)
class UserService {
    private final DatabaseUserRepository userRepository; // Прямая зависимость от инфраструктуры!

    public UserService() {
        this.userRepository = new DatabaseUserRepository(); // Жёсткая связь
    }

    public String getUserEmail(String userId) {
        User user = userRepository.findById(userId);
        return user.getEmail();
    }
}

// Модель (оставлена для контекста)
class User {
    private final String id;
    private final String email;

    public User(String id, String email) {
        this.id = id;
        this.email = email;
    }

    public String getEmail() {
        return email;
    }
}
```

**Почему это плохо:**  
- `UserService` жёстко привязан к `DatabaseUserRepository`.  
- Невозможно протестировать `UserService` без реальной базы данных.  
- Любое изменение в инфраструктуре (например, переход на другую БД) потребует изменения бизнес-логики.  
- Это классическое нарушение **Dependency Inversion Principle** (DIP) из SOLID.

---

### Объяснение и выявление инструментом

**Инструмент:** DesigniteJava  
**Правило:** *God Class* или *Feature Envy* в данном контексте не совсем точны. Но DesigniteJava содержит категорию **Architecture Violations** и конкретное правило **«Dependency Inversion Violation»** (или аналогичное в разделе «Dependency Issues»).  

**Как сработает:**  
- DesigniteJava проанализирует граф зависимостей между пакетами/классами.  
- Он обнаружит, что `UserService` (слой бизнес-логики) импортирует и использует `DatabaseUserRepository` (слой инфраструктуры) напрямую, а не через абстракцию.  
- Будет выдано предупреждение: *«Layer dependency violation: Business layer depends on Infrastructure layer»* или *«Concrete dependency instead of abstraction»*.  

**Дополнительно:**  
- **PMD** может выявить похожую проблему через правило **«LawOfDemeter»** (если цепочка вызовов идёт к инфраструктурному объекту), но лучше всего справится DesigniteJava, так как он специализируется на архитектурных проверках.  
- В среде разработки (IntelliJ IDEA) также можно настроить проверки зависимостей между модулями, что покажет красные линии при попытке импорта из инфраструктурного слоя в бизнес-слой.
