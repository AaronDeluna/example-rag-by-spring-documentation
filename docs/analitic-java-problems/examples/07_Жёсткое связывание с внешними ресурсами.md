# Жёсткое связывание с внешними ресурсами

**Категория:** Архитектурные принципы (Design for Testability)

**Описание:** Код напрямую создаёт соединения с БД, сетью или файловой системой, что делает тесты медленными и нестабильными.

**Инструменты:** DesigniteJava, PMD

---

Вот пример, демонстрирующий проблему жёсткого связывания с внешними ресурсами и её решение.

---

### Корректный пример

Используется принцип внедрения зависимостей (Dependency Injection). Код не создаёт соединение с БД сам, а получает его извне. Это позволяет легко подменять реальное соединение на mock или заглушку в тестах.

```java
import java.sql.Connection;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

// Интерфейс для работы с данными
interface UserRepository {
    String getUserEmail(int userId) throws SQLException;
}

// Реализация, использующая переданное соединение
class DatabaseUserRepository implements UserRepository {
    private final Connection connection;

    // Внедрение зависимости через конструктор
    public DatabaseUserRepository(Connection connection) {
        this.connection = connection;
    }

    @Override
    public String getUserEmail(int userId) throws SQLException {
        String query = "SELECT email FROM users WHERE id = " + userId;
        try (Statement stmt = connection.createStatement();
             ResultSet rs = stmt.executeQuery(query)) {
            if (rs.next()) {
                return rs.getString("email");
            }
            return null;
        }
    }
}

// Пример теста с mock-объектом
class UserServiceTest {
    // Тест использует mock-соединение, а не реальную БД
    void testGetUserEmail() {
        Connection mockConnection = Mockito.mock(Connection.class);
        UserRepository repo = new DatabaseUserRepository(mockConnection);
        // ... дальнейшая настройка mock и проверка
    }
}
```

**Почему это хорошо:**  
- Код не зависит от конкретного способа создания соединения.  
- Тесты могут использовать mock-объекты (через Mockito, EasyMock и т.п.), что делает их быстрыми и стабильными.  
- Легко менять источник данных (например, на тестовую БД или in-memory базу).

### Некорректный пример

Код сам создаёт соединение с БД внутри метода, что делает его жёстко связанным с конкретной базой данных и её конфигурацией.

```java
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

class UserService {
    public String getUserEmail(int userId) throws SQLException {
        // Проблема: жёсткое связывание с БД
        String url = "jdbc:mysql://localhost:3306/mydb";
        String user = "root";
        String password = "secret";

        try (Connection conn = DriverManager.getConnection(url, user, password);
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(
                 "SELECT email FROM users WHERE id = " + userId)) {

            if (rs.next()) {
                return rs.getString("email");
            }
            return null;
        }
    }
}

// Тест такого кода будет:
// 1. Зависеть от работающей БД
// 2. Медленным (реальное соединение)
// 3. Нестабильным (БД может быть недоступна)
```

---

### Объяснение и выявление инструментом

**Почему это плохо:**  
- Код жёстко привязан к конкретной БД (MySQL, URL, порт, учётные данные).  
- Тестирование требует реальной БД, что делает тесты медленными, нестабильными и сложными в настройке.  
- Нарушен принцип инверсии зависимостей (Dependency Inversion).  
- Невозможно использовать mock-объекты без рефакторинга.

**Какой инструмент выявит проблему и как:**

**PMD** — правило `AvoidThrowingRawExceptionTypes` (косвенно) или более специфичное правило `DataflowAnomalyAnalysis` может заметить, что создание соединения происходит внутри метода, а не передаётся извне.  
Однако **наиболее точное обнаружение** даёт **DesigniteJava** (или подобные статические анализаторы), которые проверяют архитектурные метрики:

- **Правило:** `Tight Coupling` или `Unnecessary Dependency on External Resources`.  
- **Как сработает:** Анализатор увидит, что класс `UserService` напрямую вызывает `DriverManager.getConnection()`, что создаёт сильную связь с конкретной реализацией JDBC-драйвера. Это будет отмечено как нарушение принципа слабой связанности (low coupling).  
- **Дополнительно:** PMD может выявить через правило `CloseResource` (ресурс не закрыт? — но здесь он закрыт через try-with-resources, так что не сработает), но основная проблема — архитектурная, а не утечка ресурсов.

**Вывод:**  
Для автоматического выявления такой проблемы лучше всего подходят инструменты архитектурного анализа (DesigniteJava, Structure101, SonarQube с правилами «избегать прямого создания внешних ресурсов»). PMD может помочь, если добавить кастомное правило, но из коробки он больше ориентирован на баги и стиль кода, а не на архитектурные антипаттерны.
