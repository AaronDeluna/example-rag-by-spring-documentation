# Отсутствие внедрения зависимостей (DI)

**Категория:** Архитектурные принципы (Design for Testability)

**Описание:** Зависимости создаются внутри класса через `new`, что не позволяет подменить их тестовыми двойниками.

**Инструменты:** DesigniteJava, PMD

---

Вот пример, демонстрирующий проблему отсутствия внедрения зависимостей (DI) и её решение, с пояснением для инструментов анализа.

---

### Корректный пример

Класс `OrderService` получает зависимость `PaymentGateway` через конструктор (внедрение зависимости). Это позволяет легко подменить реализацию в тестах.

```java
// Интерфейс для платежного шлюза
public interface PaymentGateway {
    boolean processPayment(double amount);
}

// Реальная реализация
public class RealPaymentGateway implements PaymentGateway {
    @Override
    public boolean processPayment(double amount) {
        System.out.println("Processing payment: " + amount);
        return true;
    }
}

// Класс, использующий DI
public class OrderService {
    private final PaymentGateway paymentGateway;

    // Зависимость внедряется извне
    public OrderService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void placeOrder(double amount) {
        if (paymentGateway.processPayment(amount)) {
            System.out.println("Order placed successfully");
        } else {
            System.out.println("Payment failed");
        }
    }
}

// Пример теста с подменой зависимости
public class OrderServiceTest {
    public static void main(String[] args) {
        // Создаем тестовый двойник (Mock)
        PaymentGateway mockGateway = new PaymentGateway() {
            @Override
            public boolean processPayment(double amount) {
                return true; // всегда успешно
            }
        };
        
        OrderService service = new OrderService(mockGateway);
        service.placeOrder(100.0); // Теперь можно тестировать изолированно
    }
}
```

**Почему это корректно:**
- Класс `OrderService` не создает зависимости сам.
- Тест может подменить `PaymentGateway` на mock или stub.
- Код следует принципу инверсии зависимостей (Dependency Inversion Principle).

### Некорректный пример

Класс `OrderService` создаёт зависимость `PaymentGateway` внутри себя с помощью `new`. Это жёстко связывает код с конкретной реализацией.

```java
// Плохой пример: зависимость создается внутри класса
public class OrderService {
    private PaymentGateway paymentGateway;

    public OrderService() {
        // Жесткое связывание с конкретной реализацией
        this.paymentGateway = new RealPaymentGateway();
    }

    public void placeOrder(double amount) {
        if (paymentGateway.processPayment(amount)) {
            System.out.println("Order placed successfully");
        } else {
            System.out.println("Payment failed");
        }
    }
}

// Тест становится невозможным без изменения production-кода
public class OrderServiceTest {
    public static void main(String[] args) {
        OrderService service = new OrderService();
        // Невозможно подменить paymentGateway — тест всегда использует реальный шлюз
        service.placeOrder(100.0); 
    }
}
```

---

### Объяснение и выявление инструментом

**Почему некорректный пример плох:**
1. **Нарушение тестируемости (Testability):** Нельзя подменить `RealPaymentGateway` на mock. Тест будет зависеть от реальной реализации (например, реальной платёжной системы или базы данных).
2. **Нарушение Open/Closed Principle:** Чтобы добавить новый тип шлюза, придётся менять код `OrderService`.
3. **Скрытые зависимости:** Сложнее понять, от чего на самом деле зависит класс.

**Какой инструмент выявит проблему и как:**

- **DesigniteJava:**
  - Правило: **"Tight Coupling"** (высокая связанность).
  - Как сработает: Инструмент проанализирует граф зависимостей и обнаружит, что `OrderService` напрямую создаёт экземпляр `RealPaymentGateway` через `new`. Это классический признак жёсткой связанности (coupling), который DesigniteJava помечает как нарушение.

- **PMD:**
  - Правило: **"LawOfDemeter"** (закон Деметры) или **"AvoidReassigningParameters"** (косвенно). Однако для данной проблемы точнее правило **"UseObjectForClearerAPI"** (в некоторых конфигурациях) или кастомное правило для обнаружения `new` в конструкторах.
  - Как сработает: PMD может быть настроен на поиск инстанцирования конкретных классов внутри бизнес-логики (например, через XPath-правило: `//AllocationExpression[../ClassOrInterfaceDeclaration]`). В стандартных наборах правил PMD это может быть не так явно, но при использовании расширенных профилей (например, `java-bestpractices`) он может выдать предупреждение о том, что класс создаёт свои зависимости вручную, что усложняет тестирование.

**Резюме:**  
Некорректный пример нарушает принцип внедрения зависимостей (DI), делая код немодульным и сложным для тестирования. Инструменты вроде DesigniteJava (через анализ связности) или PMD (через кастомные/расширенные правила) могут обнаружить эту проблему, указывая на прямое создание объектов внутри класса.
