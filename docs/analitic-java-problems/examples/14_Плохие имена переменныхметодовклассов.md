# Плохие имена переменных/методов/классов

**Категория:** Стиль кодирования (Clean Code)

**Описание:** Неинформативные названия (например, `a`, `temp`, `processData`).

**Инструменты:** PMD, Checkstyle

---

Вот пример, демонстрирующий проблему «Плохие имена переменных/методов/классов» и её корректное решение.

---

### Корректный пример

Код следует принципам Clean Code: имена классов, методов и переменных ясно отражают их назначение.

```java
/**
 * Класс для работы с заказами клиентов.
 */
public class OrderService {

    /**
     * Рассчитывает общую стоимость заказа с учетом налогов и скидок.
     *
     * @param order заказ, содержащий список позиций
     * @return итоговая сумма к оплате
     */
    public double calculateTotalPrice(Order order) {
        double basePrice = order.calculateSubtotal();
        double tax = basePrice * 0.2; // 20% налог
        double discount = getCustomerDiscount(order.getCustomerId());
        return basePrice + tax - discount;
    }

    /**
     * Возвращает скидку для клиента по его идентификатору.
     */
    private double getCustomerDiscount(String customerId) {
        // Логика получения скидки из базы данных
        return 10.0;
    }
}

class Order {
    private List<Item> items;

    public double calculateSubtotal() {
        return items.stream()
                    .mapToDouble(item -> item.getPrice() * item.getQuantity())
                    .sum();
    }

    public String getCustomerId() {
        return "CUST-001";
    }
}

class Item {
    private double price;
    private int quantity;

    public double getPrice() { return price; }
    public int getQuantity() { return quantity; }
}
```

**Почему это хорошо:**
- `OrderService` — понятное имя класса (отражает бизнес-логику).
- `calculateTotalPrice`, `calculateSubtotal`, `getCustomerDiscount` — глаголы, описывающие действие.
- `basePrice`, `tax`, `discount`, `order`, `customerId` — существительные, точно указывающие на данные.

### Некорректный пример

Код содержит неинформативные имена, что затрудняет его понимание и поддержку.

```java
public class A {
    public void doStuff(B b) {
        double x = b.calc();
        double y = x * 0.2;
        double z = getD(b.getC());
        double r = x + y - z;
        System.out.println(r);
    }

    private double getD(String c) {
        return 10.0;
    }
}

class B {
    private java.util.List<C> items;

    public double calc() {
        double s = 0;
        for (C item : items) {
            s += item.p * item.q;
        }
        return s;
    }

    public String getC() {
        return "CUST-001";
    }
}

class C {
    public double p;
    public int q;
}
```

**Почему это плохо:**
- `A`, `B`, `C` — абстрактные имена классов, не дающие понимания об их роли.
- `doStuff` — ничего не говорит о том, что делает метод.
- `x`, `y`, `z`, `r`, `s` — однобуквенные переменные, смысл которых неочевиден.
- `calc`, `getC`, `getD` — слишком общие имена, скрывающие реальное назначение (например, `calc` — это расчет суммы, а не просто «вычисление»).
- Публичные поля `p` и `q` вместо геттеров нарушают инкапсуляцию (но это уже другая проблема).

### Объяснение и выявление инструментом

**Почему некорректный пример плох:**
- Код сложно читать, понимать и модифицировать. Разработчику нужно тратить время на расшифровку, что такое `x`, `y`, `z` и что делает `doStuff`.
- Нарушается принцип **"intention-revealing names"** (имена, раскрывающие намерения) из Clean Code.
- В реальном проекте такой код приведет к ошибкам при рефакторинге и увеличению времени на code review.

**Какой инструмент выявит проблему и как:**

| Инструмент | Правило/проверка | Что именно сработает |
|------------|------------------|-----------------------|
| **PMD** | `ShortVariable` (по умолчанию) | Переменные `x`, `y`, `z`, `r`, `s` — длина менее 3 символов. |
| **PMD** | `ShortMethodName` | Метод `calc` — длина менее 3 символов. |
| **PMD** | `ShortClassName` | Классы `A`, `B`, `C` — длина менее 3 символов. |
| **PMD** | `AvoidFieldNameMatchingMethodName` | Поле `p` и метод `getC` — неочевидные имена (но формально не сработает, это про совпадение имен поля и метода). |
| **Checkstyle** | `LocalVariableName` (можно настроить на минимальную длину) | Переменные `x`, `y`, `z`, `s` — если задать правило `^[a-z][a-zA-Z0-9]{2,}$`. |
| **Checkstyle** | `MethodName` (с регулярным выражением) | Имя `calc` может быть отвергнуто, если требуется, чтобы метод содержал глагол и был длиннее 3 символов. |
| **PMD** | `UncommentedEmptyMethodBody` (не применимо) | Проблема не в пустых телах, а в именах. |
| **PMD** | `GodClass` / `ExcessivePublicCount` (возможно, если класс A слишком большой) | Класс `A` маленький, но если бы он рос, то сработало бы. |

**Пример настройки для PMD (правило `ShortVariable`):**
```xml
<rule ref="category/java/bestpractices.xml/ShortVariable" />
```
Оно выдаст предупреждение:  
`Avoid using short variable names like 'x' (at line 3 in A.java)`

**Пример настройки для Checkstyle (проверка имен переменных):**
```xml
<module name="LocalVariableName">
    <property name="format" value="^[a-z][a-zA-Z0-9]{2,}$"/>
    <message key="name.invalidPattern" value="Имя локальной переменной ''{0}'' должно содержать не менее 3 символов."/>
</module>
```
Это отбросит `x`, `y`, `z`, `s`.

**Итог:**  
Проблема «Плохие имена» отлично обнаруживается статическими анализаторами (PMD, Checkstyle) через правила, контролирующие минимальную длину имен и их соответствие шаблонам. Однако лучший способ — это code review и культура написания кода, а инструменты служат лишь автоматической поддержкой.
