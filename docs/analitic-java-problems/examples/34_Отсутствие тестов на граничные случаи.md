# Отсутствие тестов на граничные случаи

**Категория:** Покрытие кода

**Описание:** Не проверены крайние значения входных данных (null, пустые коллекции, максимальные/минимальные числа).

**Инструменты:** JaCoCo, JCov, Clover

---

Вот пример, демонстрирующий проблему отсутствия тестов на граничные случаи.

---

### Корректный пример

**Класс (SUT):**
```java
import java.util.List;
import java.util.Objects;
import java.util.stream.Collectors;

public class StringProcessor {
    public String joinNonNull(List<String> items, String delimiter) {
        if (items == null) {
            throw new IllegalArgumentException("items must not be null");
        }
        if (delimiter == null) {
            throw new IllegalArgumentException("delimiter must not be null");
        }
        return items.stream()
                .filter(Objects::nonNull)
                .collect(Collectors.joining(delimiter));
    }
}
```

**Тест (корректный, покрывает граничные случаи):**
```java
import org.junit.jupiter.api.Test;
import java.util.Collections;
import java.util.List;
import static org.junit.jupiter.api.Assertions.*;

public class StringProcessorTest {

    private final StringProcessor processor = new StringProcessor();

    @Test
    void joinNonNull_shouldThrowWhenItemsIsNull() {
        assertThrows(IllegalArgumentException.class,
                () -> processor.joinNonNull(null, ","));
    }

    @Test
    void joinNonNull_shouldThrowWhenDelimiterIsNull() {
        assertThrows(IllegalArgumentException.class,
                () -> processor.joinNonNull(List.of("a"), null));
    }

    @Test
    void joinNonNull_shouldReturnEmptyStringForEmptyList() {
        String result = processor.joinNonNull(Collections.emptyList(), ",");
        assertEquals("", result);
    }

    @Test
    void joinNonNull_shouldFilterOutNullElements() {
        List<String> items = List.of("a", null, "b", null, "c");
        String result = processor.joinNonNull(items, "-");
        assertEquals("a-b-c", result);
    }

    @Test
    void joinNonNull_shouldHandleSingleElement() {
        List<String> items = List.of("only");
        String result = processor.joinNonNull(items, ",");
        assertEquals("only", result);
    }

    @Test
    void joinNonNull_shouldHandleAllNullElements() {
        List<String> items = List.of(null, null, null);
        String result = processor.joinNonNull(items, ",");
        assertEquals("", result);
    }
}
```

### Некорректный пример

**Класс (SUT) – тот же, что и выше.**

**Тест (некорректный, отсутствуют граничные случаи):**
```java
import org.junit.jupiter.api.Test;
import java.util.List;
import static org.junit.jupiter.api.Assertions.*;

public class StringProcessorTest {

    private final StringProcessor processor = new StringProcessor();

    @Test
    void joinNonNull_shouldJoinStringsWithDelimiter() {
        List<String> items = List.of("a", "b", "c");
        String result = processor.joinNonNull(items, ",");
        assertEquals("a,b,c", result);
    }

    @Test
    void joinNonNull_shouldHandleMixedNulls() {
        List<String> items = List.of("x", null, "y");
        String result = processor.joinNonNull(items, "|");
        assertEquals("x|y", result);
    }
}
```

---

### Объяснение и выявление инструментом

**Почему некорректный пример плох:**

1. **Не проверен `null` для аргументов `items` и `delimiter`.** Если кто-то передаст `null`, код упадёт с `NullPointerException` (в текущей реализации) или с `IllegalArgumentException` (если защита есть, но не протестирована). Без теста на `null` это останется незамеченным до прогона в production.
2. **Не проверена пустая коллекция.** Метод может вернуть пустую строку, но тест этого не проверяет. Если позже реализация изменится (например, начнёт бросать исключение для пустого списка), тест это не поймает.
3. **Не проверен случай, когда все элементы `null`.** Логика фильтрации может дать сбой, если список целиком состоит из `null`.
4. **Не проверен случай с одним элементом.** Граничное значение размера коллекции (1) часто является источником ошибок (например, неправильная обработка разделителя).
5. **Покрытие кода (line/branch coverage) будет высоким, но неполным с точки зрения граничных значений.** Инструменты покрытия покажут, что строки кода выполнены, но не покажут, что все логические пути пройдены (например, ветка `if (items == null)` не тестируется).

**Какой инструмент и как выявит проблему:**

- **JaCoCo** (или **JCov**, **Clover**) при анализе покрытия покажет:
  - **Branch coverage** для условий `items == null` и `delimiter == null` будет равен **0%** (ни одна ветка `true` не выполнена).
  - **Line coverage** для строк `throw new IllegalArgumentException(...)` будет равен **0%** (эти строки ни разу не выполнялись).
  - **Branch coverage** для `filter(Objects::nonNull)` может быть неполным, если не проверен случай, когда все элементы `null` (ветка `nonNull` не даст ни одного элемента, но это может быть скрыто).

- **Конкретное правило/проверка:**  
  В отчёте JaCoCo (например, в HTML-отчёте) для класса `StringProcessor` будет показано, что:
  - Условие `items == null` имеет только одну покрытую ветку (`false`), ветка `true` не покрыта.
  - Условие `delimiter == null` — аналогично.
  - Это явно указывает на пробел в тестировании граничных случаев (null-аргументы).

**Вывод:** Даже при 100% покрытии строк (line coverage) можно пропустить важные граничные случаи. Инструменты покрытия ветвлений (branch coverage) помогают выявить такие пробелы. Для полной гарантии необходимо дополнительно использовать мутационное тестирование (например, PIT), которое проверит, действительно ли тесты ловят изменения в логике.
