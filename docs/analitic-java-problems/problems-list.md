## 📋 Список проработанных проблем (нарушений качества)

### 🔹 Группа «Архитектурные принципы»

#### SOLID
| № | Название проблемы | Краткое описание |
|---|-------------------|-------------------|
| 1 | **Нарушение принципа единственной ответственности (SRP)** | Класс выполняет несколько несвязанных задач (например, одновременно работает с БД, генерирует отчёты и отправляет email). |
| 2 | **Нарушение принципа открытости/закрытости (OCP)** | Класс требует модификации для добавления нового поведения, вместо расширения через наследование или интерфейсы. |
| 3 | **Нарушение принципа подстановки Лисков (LSP)** | Подкласс не может заменить родительский класс без изменения ожидаемого поведения (например, переопределяет метод с нарушением контракта). |
| 4 | **Нарушение принципа разделения интерфейсов (ISP)** | «Толстый» интерфейс, который заставляет классы реализовывать неиспользуемые методы. |
| 5 | **Нарушение принципа инверсии зависимостей (DIP)** | Код зависит от конкретных реализаций, а не от абстракций (интерфейсов), что усложняет тестирование и замену компонентов. |

#### Design for Testability
| № | Название проблемы | Краткое описание |
|---|-------------------|-------------------|
| 6 | **Использование статических методов/полей** | Затрудняет мокирование и изоляцию при тестировании. |
| 7 | **Жёсткое связывание с внешними ресурсами** | Код напрямую создаёт соединения с БД, сетью или файловой системой, что делает тесты медленными и нестабильными. |
| 8 | **Отсутствие внедрения зависимостей (DI)** | Зависимости создаются внутри класса через `new`, что не позволяет подменить их тестовыми двойниками. |
| 9 | **Синглтоны и глобальные состояния** | Тесты начинают влиять друг на друга из-за общего изменяемого состояния. |

#### Чистая архитектура
| № | Название проблемы | Краткое описание |
|---|-------------------|-------------------|
| 10 | **Нарушение правила зависимостей** | Зависимости направлены от бизнес-логики к инфраструктуре, а не наоборот. |
| 11 | **Смешивание бизнес-логики и инфраструктурного кода** | Например, прямое использование аннотаций фреймворка (Spring, JPA) в доменных классах. |

### 🔹 Группа «Стиль кодирования и читаемость»

#### Clean Code
| № | Название проблемы | Краткое описание |
|---|-------------------|-------------------|
| 12 | **Слишком длинный метод** | Метод содержит более 20–30 строк, делает много разных вещей. |
| 13 | **Дублирование кода** | Одинаковые фрагменты кода встречаются в разных местах. |
| 14 | **Плохие имена переменных/методов/классов** | Неинформативные названия (например, `a`, `temp`, `processData`). |
| 15 | **Комментарии вместо самодокументирования** | Код настолько запутан, что требует пояснений, которые дублируют логику. |
| 16 | **Пустые блоки catch** | Игнорирование исключений без логирования. |
| 17 | **Избыточные объекты** | Создание объектов, которые можно не создавать (например, `String` вместо `StringBuilder` в циклах). |
| 18 | **Длинный список параметров** | Метод принимает более 3–4 аргументов, что усложняет чтение и тестирование. |

#### Google Java Style Guide
| № | Название проблемы | Краткое описание |
|---|-------------------|-------------------|
| 19 | **Нарушение форматирования** | Неправильные отступы, длина строки >100 символов, нарушение порядка импортов. |
| 20 | **Нарушение правил именования** | Пакеты, классы, методы, константы названы не по стандарту (например, `userService` вместо `UserService` для класса). |
| 21 | **Отсутствие JavaDoc для публичных API** | Не описано назначение и параметры публичных методов и классов. |

### 🔹 Группа «Запахи тестов» (Test Smells)

#### Из книги Месароша
| № | Название проблемы | Краткое описание |
|---|-------------------|-------------------|
| 22 | **Assertion Roulette** | Один тест содержит несколько проверок (`assert`), и при падении непонятно, какая из них вызвала ошибку. |
| 23 | **Eager Test** | Тест проверяет сразу множество различных условий, нарушая принцип единой ответственности в тесте. |
| 24 | **Conditional Test Logic** | Внутри теста присутствуют условные операторы (`if`, `switch`), что делает тест недетерминированным и сложным. |
| 25 | **Fragile Test** | Тест ломается при изменениях, не связанных с тестируемой логикой (например, при изменении имени метода). |
| 26 | **Obscure Test** | Тест сложно понять из-за плохого именования, избыточной подготовки или отсутствия комментариев. |
| 27 | **Slow Tests** | Тесты выполняются слишком долго (например, используют реальную БД, сеть, `Thread.sleep`). |
| 28 | **Test Code Duplication** | Один и тот же код подготовки данных или проверок повторяется в нескольких тестах. |
| 29 | **Redundant Assertion** | Тест содержит проверки, которые всегда истинны (например, проверка того же значения, которое только что было установлено). |
| 30 | **Indirect Testing** | Тест проверяет поведение через побочные эффекты, а не через явные результаты. |
| 31 | **Mystery Guest** | Использование внешних данных или конфигураций, которые не очевидны из кода теста. |

### 🔹 Группа «Покрытие кода»

| № | Название проблемы | Краткое описание |
|---|-------------------|-------------------|
| 32 | **Недостаточное покрытие строк** | Многие строки кода не выполняются ни одним тестом. |
| 33 | **Недостаточное покрытие ветвей** | Не проверены логические ветви (например, все варианты `if/else`). |
| 34 | **Отсутствие тестов на граничные случаи** | Не проверены крайние значения входных данных (null, пустые коллекции, максимальные/минимальные числа). |
| 35 | **Непокрытые исключения** | В коде есть блоки `catch`, которые не покрываются тестами, что может скрывать ошибки. |

## 🧩 Как использовать этот список

1. Выберите из списка конкретную проблему (например, «Assertion Roulette» или «Нарушение SRP»).
2. Заполните мета-промпт, указав название, описание, категорию и подходящие инструменты.
3. Отправьте запрос AI и получите готовый пример корректного/некорректного кода.

Этот список покрывает основные аспекты качества кода и тестов на Java, которые можно проверять с помощью перечисленных инструментов (Checkstyle, PMD, SpotBugs, DesigniteJava, TestSmellDetector, AromaDr, JaCoCo и др.).
