
### 1. Кто принимает решение о вызове

| Сценарий | Кто инициирует вызов | Роль пользователя |
|----------|----------------------|-------------------|
| Прямой вызов MCP‑инструментов | Модель выбирает конкретный инструмент из списка на каждом шаге | Задаёт цель, может попросить использовать определённый инструмент |
| Skill, оформленный как инструмент | Модель решает, вызвать ли навык, наравне с любым другим инструментом | Может потребовать «используй навык X» |
| Skill вне контура модели (внешний workflow) | Пользователь запускает навык кнопкой/командой | Прямой выбор |

**Вывод:** В типовой LLM‑архитектуре оба варианта — и прямой MCP‑инструмент, и skill — **выбираются моделью**. Пользователь может влиять формулировкой инструкции, но финальный триггер всегда модельный.

---

### 2. Может ли skill вызывать модель

Да, это стандартный паттерн. Внутри навыка может происходить:
- обращение к LLM для анализа промежуточных данных,
- динамическая генерация дочерних запросов к MCP‑серверу,
- ветвление логики с участием модели,
- итоговая суммаризация.

Таким образом, skill способен **вложенно использовать ту же самую (или другую) модель**, создавая дополнительные, скрытые от пользователя раунды LLM‑вызовов.

---

### 3. Деревья вызовов навыков: статические и динамические

Skill может оркестрировать сложные цепочки и деревья вызовов:
- **Статическое дерево** — жёстко прописанная кодом последовательность навыков и MCP‑инструментов, где модель используется только как обработчик на отдельных узлах.
- **Динамическое дерево** — на каждом шаге навык спрашивает модель «что делать дальше?», и модель выбирает следующий навык или возврат к прямым инструментам.

**Важный нюанс:** даже в статическом дереве начальный выбор навыка и последующие решения о необходимости его вызова остаются за моделью (или за другим навыком, который тоже управляется моделью). То есть модель не теряет свободу выбора траектории — она просто оперирует более крупными, заранее собранными блоками.

---

### 4. Количество вызовов: прямое сравнение с учётом всех факторов

#### 4.1 С точки зрения модели (LLM‑раунды)
- **Прямой доступ к MCP:** модель пошагово вызывает десятки атомарных инструментов — каждый требует отдельного раунда «думай → вызывай → результат → снова думай». Очень много итераций.
- **Вызов через навык:** модель вызывает навык за 1 раунд. Даже если внутри навыка есть скрытые обращения к LLM, модель верхнего уровня в этих обращениях не участвует. **Чем выше уровень абстракции навыка, тем меньше LLM‑раундов на единицу полезной работы**.
- **Динамическое дерево навыков:** модель верхнего уровня может последовательно вызывать несколько навыков, строя цепочку/дерево своими решениями. Это увеличивает число её раундов по сравнению с одним «всеобъемлющим» навыком, но обычно всё равно меньше, чем при прямом управлении каждым MCP‑инструментом.

#### 4.2 С точки зрения MCP‑сервера (сетевые запросы)
- **Прямые вызовы модели:** модель часто перепроверяет, зацикливается, делает избыточные пробные запросы. Количество операций MCP непредсказуемо растёт.
- **Skill (любого типа):** логика фиксирована или управляется заложенными правилами, а не «свободным поиском» модели. Хорошо спроектированный навык минимизирует избыточные запросы (кеш, параллельные вызовы, проверенные цепочки). Однако:
    - Если навык делает дополнительные MCP‑вызовы для валидации, логирования или обогащения, общее число запросов может незначительно возрасти.
    - В динамическом дереве модель может запросить больше веток, чем реально необходимо, если её стратегия не оптимизирована.

**Результирующая:** при грамотной упаковке логики в навыки суммарное число запросов к MCP‑серверу **обычно ниже**, чем в свободном ReAct‑цикле модели. При неграмотной — может быть сравнимым или даже бо́льшим.

#### 4.3 Главный фактор: свобода выбора траектории у модели
Ваше уточнение точно отражает реальность: **модель всегда принимает решение, какой навык вызвать следующим** (даже если навык сам внутри вызывает другие навыки). Это означает, что результат по количеству вызовов сильно зависит от «разумности» модели и качества проектирования навыков. Возможны крайние случаи:
- Модель, получив навык `deep_research`, вызывает его один раз. Внутри навыка — 50 эффективных MCP‑запросов и 5 скрытых LLM‑раундов. Снаружи — 1 модельный шаг. Минимум накладных расходов.
- Та же модель, имея доступ к набору микросервисных навыков, может начать строить глубокое динамическое дерево, вызывая десятки навыков по очереди, каждый из которых делает 1‑2 MCP‑запроса. Итоговое число модельных раундов и MCP‑запросов будет сопоставимо с прямым использованием инструментов, но с лучшей декомпозицией.

### 5. Итоговая система координат

| Параметр                     | Прямой MCP (модель)                 | Skill (как инструмент модели)               |
|------------------------------|-------------------------------------|---------------------------------------------|
| Уровень дробления действий   | Атомарные инструменты               | Агрегированные, композитные навыки          |
| Кто выбирает действие        | Модель на каждом шагу               | Модель на уровне выбора навыков; внутри skills возможны свои сценарии |
| Количество LLM‑раундов       | Максимальное (ReAct loop)           | Значительно ниже, если навык инкапсулирует много действий |
| Количество MCP‑запросов      | Склонно к избыточности              | При оптимизации — минимально необходимое, при неоптимизации — сопоставимо |
| Глубина возможного дерева    | Практически линейная цепочка        | Статические или динамические деревья любой вложенности |
| Свобода выбора траектории    | Полная (модель видит всё)           | Полная на верхнем уровне; внутренняя траектория либо жёсткая, либо управляется отдельными LLM‑вызовами |
| Прозрачность для пользователя| Каждый инструмент виден в логе       | Высокоуровневый вызов, детали скрыты |

**Ключевое заключение:**
Модель всегда сохраняет свободу выбора траектории — она решает, инициировать ли навык, какой именно и в какой последовательности. Разница лишь в «высоте» этой свободы: при прямом доступе к MCP она управляет каждым низкоуровневым шагом, при использовании навыков — оперирует крупными блоками, внутри которых либо алгоритм, либо вложенная модель реализует детали. Именно это переключение с микро‑менеджмента на макро‑управление даёт основной выигрыш в скорости, стоимости и предсказуемости поведения.

### Composite Skills

**Composite Skills** - архитектурный подход к созданию составных навыков.
По сути, skill — это не просто обёртка над одним MCP‑инструментом, а оркестратор, который внутри может выстраивать деревья вызовов других skills, инструментов и моделей.

### Как это работает технически

**1. Прямая кодовая композиция (статические деревья)**
Skill реализован как функция или рабочий процесс, который явно вызывает другие зарегистрированные навыки через их API (без участия модели). Например, навык `investigate_incident` может внутри себя последовательно вызвать:
- `mcp__fetch_logs` → `analyze_logs_skill` → `summarize_skill`

  При этом `analyze_logs_skill` сам может быть деревом, внутри которого вызываются ещё более мелкие навыки. Получается дерево, где узлы — это навыки, а рёбра — жёстко прописанная логика. Модель здесь не участвует в принятии решений о вызовах, она лишь может быть использована на отдельных узлах для обработки данных.

**2. Модельно-управляемая композиция (динамические деревья)**

Skill содержит внутри обращение к LLM, которая на основе промежуточных результатов решает, какой навык (или MCP‑инструмент) вызвать следующим. Это порождает цепочки и деревья вызовов, определяемые на лету. Например, навык `deep_research`:

- вызывает MCP‑поиск,
- отправляет результат модели с промптом «Нужно ли углубиться в какой-то подпункт?»,
- модель решает вызвать `expert_analysis_skill` для одного из документов,
- `expert_analysis_skill` в свою очередь может снова вызвать модель и другие навыки.
  Так образуется дерево, где решения принимаются моделью, но инициированы из навыка, а не напрямую пользователем.

### Итог
Выстраивание деревьев навыков — это не просто возможно, а является ключевым подходом к созданию сложных агентных систем. В отличие от ситуации, где модель напрямую дёргает десятки MCP‑инструментов в длинной итерации, дерево навыков даёт структуру, переиспользование и кардинально сокращает число необходимых обращений и к LLM, и к серверам MCP. Однако этот выигрыш достигается только при осознанном проектировании, иначе можно получить обратный эффект — каскад лишних вызовов.
