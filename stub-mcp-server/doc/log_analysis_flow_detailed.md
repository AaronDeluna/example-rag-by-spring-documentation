# Агентный пайплайн анализа логов — детализированная схема (источники + поток)

Это **второй, более «широкий» вид** той же системы, что и в первой схеме. Первая схема показывала внутреннюю логику туллов (кластеризатор → поисковик → анализатор → агрегатор). Эта показывает:

- **откуда берутся данные** (реальные источники: Allure, TestOps, Jenkins, логи из MCP-серверов и т.д.);
- **нумерованный поток оркестрации** вокруг `Gigacode CLI/Core Agent` (шаги 1–5);
- **что складывается на выход** (Json-артефакты + HTML-инсайт за период).

Связка со схемой №1: `Субагент 1` здесь = весь блок туллов из первой схемы, а `Json`-боксы = `Хранилище`.

---

## Действующие лица

### Источники данных (вход)

| Группа | Источники | Куда сходятся |
|---|---|---|
| **Контекст скилла** | `Профиль`, `План` | → `SKILL` |
| **Отчёты о прогонах** | `Jenkins`, `TestOps`, `Локальный запуск` | → `Allure-отчёт` |
| **Ошибки приложения** | `Трейс с ошибкой из приложения` (в т.ч. от сопроводов) | → напрямую в Gigacode |
| **Логи** | `DBP-логгер` → `MCP-сервер DBP-логгер`; `Единый Аудит`, `Тенгри` → `MCP-сервер Тенгри`; `КУПК` | → сводятся в `Логи` |

### Ядро

- **`Gigacode CLI/Core Agent`** — центральный оркестратор. Собирает все входы, раздаёт задачи субагенту, формирует выход.

### Субагент 1 (аналитический блок)

- **`MCP-сервер кластеризатор.анализатор`** — точка входа в субагента.
- **`Тула кластеризатор`** — кластеризация (шаг 3.1).
- **`Тула анализатор`** — анализ (шаг 3.2).
- **`Тула агрегатор отчётов`** — сборка отчёта (шаг 3.3).
- **`Тулл поисковик`** — поиск по хранилищу.
- **`Сходить в MCP за доп. логами`** — ветка дозапроса, когда данных не хватило.

### Выход

- **`Json`** (несколько) — сохранённые артефакты по каждому инциденту → это и есть хранилище.
- **`HTML с общими инсайтами за период`** — агрегированный отчёт, собирается из накопленных Json.

---

## Поток по шагам (нумерация со схемы)

### Шаг 1. Получение данных
`Gigacode CLI/Core Agent` **собирает входные данные** со всех источников:
- `Allure-отчёт` (собранный из Jenkins / TestOps / локального запуска);
- `Трейс с ошибкой` из приложения (в том числе прилетевший от сопроводов);
- `Логи` (см. шаг 5);
- контекст скилла (см. шаг 2).

### Шаг 2. Передача скилла с планом и профилем
`SKILL` **передаёт в Gigacode** контекст: `План` + `Профиль`.
> Это задаёт агенту рамку: что за прогон, какой план/окружение, чей профиль. По сути — конфиг запуска.

### Шаг 3. Передача для анализа → Субагент 1
`Gigacode` **отправляет собранный пакет данных** в `MCP-сервер кластеризатор.анализатор` — вход в `Субагент 1`. Внутри субагента:

- **3.1 Кластеризация** → `Тула кластеризатор`
  - Логи/трейсы группируются в кластеры.
  - Параллельно: **«сходим в хранилище и проверим, есть ли такие кейсы»** (через `Тулл поисковик`) — не видели ли мы это событие раньше.

- **3.2 Анализ** → `Тула анализатор`
  - Незнакомые кластеры уходят в анализ.
  - Развилка **«Достаточно инфо?»**:
    - **Нет** → `Сходить в MCP за доп. логами` → **«проверить, есть ли такой артефакт»** (сверка с `Json`-хранилищем) → добор логов и **повтор цикла** (это шаг 5, обратная петля).
    - **Да** → идём в отчёт (3.3).

- **3.3 Отчёт** → `Тула агрегатор отчётов`
  - Формируется итоговый отчёт по кластеру/инциденту.

### Шаг 4. Возврат отчёта
`Субагент 1` (через `MCP-сервер кластеризатор.анализатор`) **возвращает готовый отчёт** обратно в `Gigacode`.

### Шаг 5. Дозапрос логов (обратная петля)
Когда на шаге 3.2 данных не хватило — система идёт в **MCP-серверы за доп. логами** (`DBP-логгер`, `Тенгри` и т.д.), новые `Логи` **возвращаются в Gigacode**, и цикл кластеризации/анализа повторяется на расширенном наборе.
> Это тот же цикл самодообогащения, что оранжевая петля на схеме №1.

---

## Выход системы

После возврата отчёта `Gigacode` формирует артефакты:

1. **`Json` (по каждому артефакту)** — сохраняется в хранилище. На базе текущего артефакта **формируются рекомендации**: инцидент / доработка / бакфикс.
2. **`HTML с общими инсайтами за период`** — агрегируется из накопленных `Json`. Это отчёт «инсайт за период» (Сценарий B из схемы №1): берём всё, что накопили прошлые прогоны, и сводим в один HTML.

---

## Итоговый маршрут (кратко)

```
Источники (Allure / трейсы / логи / skill)
      │  1. Получение данных  +  2. Скилл (план+профиль)
      ▼
Gigacode CLI/Core Agent
      │  3. Передача для анализа
      ▼
Субагент 1:  3.1 Кластеризация → (поиск в хранилище)
             3.2 Анализ → «Достаточно инфо?»
                   ├── Нет → MCP за доп. логами → (5) назад в Gigacode → повтор
                   └── Да  → 3.3 Отчёт (агрегатор)
      │  4. Возврат отчёта
      ▼
Gigacode → Json (хранилище, рекомендации: инцидент/доработка/бакфикс)
        → HTML с общими инсайтами за период
```

---

## Как две схемы стыкуются

| Схема №1 (логика туллов) | Схема №2 (эта, источники + поток) |
|---|---|
| Артефакт (набор логов) + запрос | Собирается из Allure / трейсов / логов на шагах 1–2 |
| Тулл кластеризатор / поисковик / анализатор / агрегатор | Всё внутри `Субагент 1` |
| Хранилище | `Json`-боксы |
| Оранжевая петля «добор логов через смеж. MCP» | Ветка «Нет → сходить в MCP за доп. логами» + шаг 5 |
| Сценарий B «инсайт за период» | `HTML с общими инсайтами за период` |

## Открытые вопросы по реализации (не читается из схемы)

- **Кто собирает Allure-отчёт** — Gigacode сам дёргает Jenkins/TestOps, или отчёт уже готовый кладётся на вход?
- **Формат `Логи`** — единый нормализованный формат после MCP-серверов, или каждый сервер отдаёт своё, и нормализация уже в Gigacode?
- **Лимит петли шага 5** — сколько раз можно ходить за доп. логами, прежде чем остановиться и вернуть «данных недостаточно».
- **Триггер HTML-инсайта** — он собирается по расписанию (за период) или по запросу пользователя? От этого зависит, где живёт агрегация Json → HTML.
- **`Профиль` и `План`** — что именно в них (профиль пользователя/сервиса? план тестирования?). Влияет на то, как скилл конфигурирует прогон.
