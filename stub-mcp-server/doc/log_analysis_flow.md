# Агентный пайплайн анализа логов — полный контекст по шагам

Документ описывает, как работает система по приложенной схеме. Есть **две точки входа** (два сценария), которые расходятся сразу после `Gigacode CLI/Core Agent`, и общий слой инструментов (туллов) + `Хранилище`.

---

## Действующие лица (компоненты)

| Компонент | Роль |
|---|---|
| **Gigacode CLI / Core Agent** | Точка входа. Принимает вызов skill и маршрутизирует запрос по одному из двух сценариев |
| **Тулл кластеризатор** | Группирует сырые логи из артефакта в кластеры |
| **Тулл поисковик** | Ищет соответствия кластеров в Хранилище (уже известные события) |
| **Тулл анализатор** | Анализирует незнакомые кластеры, решает, хватает ли данных |
| **Тулл агрегатор отчетов** | Собирает/сохраняет отчёт, отдаёт ответ через MCP |
| **Оркестратор** | Управляет циклом дозапроса данных, финально возвращает ответ пользователю |
| **Хранилище** | Персистентное хранилище событий/отчётов |
| **Пользователь** | Получатель финального ответа |

---

## Точка входа

1. **Вызов / начало работы** → вызывается **skill**.
2. Skill поднимает **Gigacode CLI / Core Agent**.
3. Core Agent смотрит на тип запроса и уходит в один из двух сценариев:
   - **Сценарий A** — на входе есть *артефакт (набор логов) + запрос пользователя* → полный разбор логов.
   - **Сценарий B** — запрос вида *«предоставить инсайт за период»* → быстрый сбор готовых данных из Хранилища.

---

## Сценарий A. Разбор артефакта с логами

### Шаг 1. Вход
- На вход приходит **артефакт (набор логов)** и **запрос пользователя**.
- Core Agent **передаёт** это в `Тулл кластеризатор`.

### Шаг 2. Кластеризация
- `Тулл кластеризатор` разбивает логи на кластеры и **возвращает ответ** — *кластеризованную выдержку из артефактов*.
- Выдержка **передаётся** дальше в `Тулл поисковик`.

### Шаг 3. Поиск по Хранилищу
- `Тулл поисковик` делает **поиск соответствий по полученным кластерам** в `Хранилище`.
- Тут же работает **цикл обработки JSON с ошибками**: если ответ/данные приходят кривым JSON, поисковик крутит их через себя (self-heal / retry), пока не распарсит корректно.

### Шаг 4. Решение «Нашёл?»
Ключевая развилка — нашлось ли соответствие кластера в Хранилище.

#### Ветка «Да» (событие уже известно)
1. Поисковик **отправляет событие для сохранения** в Хранилище.
2. Управление уходит в `Тулл агрегатор отчетов`.
3. Агрегатор **сохраняет** событие в `Хранилище`.
4. **Возвращает ответ от MCP** → `Оркестратор`.
5. Оркестратор делает **возврат ответа** → **Пользователю**.
   > Это «счастливый путь»: событие знакомое, ничего доанализировать не нужно.

#### Ветка «Нет» (незнакомый кластер)
1. Поисковик **отправляет кластер для анализа** в `Тулл анализатор`.
2. `Тулл анализатор` анализирует кластер и решает: **«Достаточно данных в кластерах?»**

### Шаг 5. Развилка анализатора «Достаточно данных?»

#### «Да» — данных хватает
- Анализатор отдаёт результат в `Тулл агрегатор отчетов`.
- Дальше — как в ветке «Да» выше: **сохранить** в Хранилище → **вернуть ответ от MCP** → `Оркестратор` → **Пользователь**.

#### «Нет» — данных не хватает (цикл дозапроса)
1. Анализатор делает **возврат ответа MCP** → `Оркестратор`.
2. Оркестратор запускает план: **«идём по смежным MCP и собираем доп. логи»**.
3. Собранные доп. логи **по обратной связи возвращаются в `Тулл кластеризатор`** (оранжевая петля на схеме).
4. Весь цикл (кластеризация → поиск → анализ) **повторяется** уже на расширенном наборе логов.
   > Это главный цикл самодообогащения: система сама добирает недостающий контекст, пока анализатору не хватит данных, чтобы закрыть кластер.

---

## Сценарий B. Инсайт за период (без разбора артефакта)

1. Core Agent получает **запрос пользователя «предоставить инсайт за период»**.
2. Идёт **вызов СубАгента** → `Тулл агрегатор отчетов`.
3. Агрегатор **получает данные** из `Хранилища` (уже накопленные ранее события/отчёты).
4. Возвращает пользователю готовый инсайт за запрошенный период.
   > Здесь нет кластеризации и анализа — берём то, что уже собрано в Хранилище прошлыми прогонами Сценария A.

---

## Итоговые пути (кратко)

**A. Событие известно:**
`артефакт+запрос → кластеризатор → поисковик → (Нашёл: Да) → агрегатор → Хранилище → MCP → Оркестратор → Пользователь`

**A. Событие новое, данных хватает:**
`... поисковик → (Нашёл: Нет) → анализатор → (Достаточно: Да) → агрегатор → Хранилище → MCP → Оркестратор → Пользователь`

**A. Событие новое, данных не хватает (петля):**
`... анализатор → (Достаточно: Нет) → MCP → Оркестратор → добор логов по смежным MCP → назад в кластеризатор → повтор`

**B. Инсайт за период:**
`запрос за период → СубАгент → агрегатор → Хранилище → инсайт пользователю`

---

## Ключевые механики, на которые стоит обратить внимание

- **Две роли у агрегатора отчётов.** Он и финализирует результат Сценария A (сохранить + отдать через MCP), и обслуживает Сценарий B (достать инсайт из Хранилища). По сути единая точка записи/чтения отчётов.
- **Хранилище — общая память.** Сценарий A наполняет его событиями, Сценарий B из него читает. Чем больше прогонов A, тем полезнее B.
- **Петля дозапроса через Оркестратор** — единственное место, где система выходит за пределы исходного артефакта и лезет в смежные MCP за доп. логами. Тут нужен контроль на зацикливание (лимит итераций / бюджет).
- **Цикл обработки JSON с ошибками** в поисковике — локальный self-heal парсинга, не путать с большой петлёй Оркестратора.

## Вопросы, которые стоит закрыть по реализации (не видно из схемы)

- Есть ли **лимит итераций** у оранжевой петли, чтобы Оркестратор не собирал доп. логи бесконечно?
- По какому критерию `Тулл поисковик` считает, что кластер «нашёлся» (порог похожести, ключ, эмбеддинги)?
- Что именно `Тулл анализатор` понимает под «достаточно данных» — эвристика, порог, отдельная модель?
- Идемпотентно ли **сохранение события** в Хранилище (не плодим дубли при повторных прогонах)?
