# Миграция статического утилитарного класса на интерфейсную архитектуру

Используйте этот навык, когда нужно заменить статический класс-утилиту (с if-else по ОС, захардкоженными путями, сборкой команд) на гибкую интерфейсную архитектуру с конфигурацией через `.properties` и возможностью подключать разные реализации.

## Типичный сценарий

Есть класс вида:
```java
public final class StaticFactory {
    public static List<String> buildCommand(String prompt) {
        // if-else по ОС, захардкоженные пути
        // сложно тестировать, нельзя подменить
    }
}
```

Нужно получить систему вида:
```java
public interface CommandFactory {
    List<String> buildCommand(String prompt, Path logDir);
}
public class Impl implements CommandFactory {
    // настраивается через properties, использует интерфейс для поиска путей
}
```

## Процесс (6 шагов)

### Шаг 1: Создать новые компоненты (интерфейсы + реализации)

Пакет для новых классов — `util.<domain>` (например, `util.cli`).

**Что создаётся:**
1. **Enum определения ОС** — единый источник истины об ОС (WINDOWS, MAC, LINUX, OTHER) с `detect()`.
2. **Интерфейс разрешения путей** — `resolveExecutable(String name)`. Отделяет поиск файла от сборки команды.
3. **Реализация разрешения путей** — поиск в PATH, затем fallback-пути для текущей ОС. Поддерживает два режима: путь указывает на конкретный файл (например, `/path/to/cli-entry.js`) или на директорию (ищет внутри файл с именем команды).
4. **Интерфейс сборки команды** — `buildCommand(String prompt, Path logDir)`. Абстрагирует способ построения командной строки.
5. **Реализация сборки команды** — принимает resolver, базовые аргументы, префикс (для Windows). Собирает команду в фиксированном порядке: `[префикс] executable [аргументы] [логирование] prompt`.
6. **Новое исключение** — для случаев, когда исполняемый файл не найден (наследует существующее исключение конфигурации, если такое есть).

**TDD (RED):**
- Тесты на `detect()` для всех трёх ОС (Linux, macOS, Windows)
- Тесты на разрешение путей: поиск в PATH, fallback как файл, fallback как директория, исключение при ненайденном
- Тесты на сборку команды: без logDir, с logDir, префикс Windows, неизменяемость списка
- Тест на наследование нового исключения

**Важно:** Использовать уникальные имена команд в тестах (не `qwen`, а `my-custom-cli-123`), чтобы тест не прошёл случайно на системе, где эта команда есть в PATH.

### Шаг 2: Добавить конфигурацию (.properties)

**Новые параметры в `*-runner.properties`:**
```properties
# Fallback-пути для каждой ОС (разделитель ;)
agent.cli.qwen.fallback.linux=/path1;/path2
agent.cli.qwen.fallback.windows=C:\\path\\to\\exe
agent.cli.qwen.fallback.mac=/path

# Базовые аргументы (разделитель ,)
agent.cli.qwen.args=--arg1,--arg2,--arg3

# Префикс для Windows (разделитель ,)
agent.cli.qwen.prefix.windows=cmd.exe,/c
```

**Файлы:**
1. `src/main/resources/agent-runner.properties` — шаблон для приложения с комментариями
2. `src/test/resources/agent-runner.properties` — для тестов (может переопределять)

**Методы чтения:** статические, принимающие `Properties` (stateless), возвращающие пустой список при отсутствии свойства. Разделители: `;` для путей, `,` для аргументов.

**TDD (RED):**
- Чтение fallback-путей для каждой ОС из Properties
- Чтение базовых аргументов
- Чтение префикса (только для Windows, для других ОС — пустой список)
- Значения по умолчанию при отсутствии свойств
- Обработка пустых строк и пробелов вокруг разделителей

### Шаг 3: Адаптировать фабрику

Фабрика, которая создаёт основные классы (раннеры), должна:
1. Получить метод для создания новой `CommandFactory` из `Properties` — строит fallback-карту через методы чтения из Шага 2, создаёт resolver и реализацию сборки команды.
2. Передавать `CommandFactory` в конструктор раннера (вместо старого статического вызова).
3. Если конструктор раннера требует дополнительных зависимостей (например, `RunnerLogWriter`), которые раньше создавались внутри — добавлять их как поля фабрики.

**Метод создания фабрики** должен быть как минимум package-private (чтобы сервисы в том же пакете могли использовать его для создания `CommandFactory` по умолчанию).

**Критично:** после этого шага фабрика НЕ создаёт раннер без `CommandFactory`.

### Шаг 4: Переработать потребителей (раннеры) — убрать старые конструкторы

1. Добавить поле `CommandFactory` в классы-потребители (оба раннера).
2. Единственный конструктор — с `CommandFactory`. Все старые конструкторы удаляются.
3. Все вызовы `StaticFactory.buildCommand()` заменяются на `commandFactory.buildCommand()`.
4. Удалить импорт старого статического класса.

**Побочные эффекты (обязательно проверить `grep -rn "new Consumer"`):**
- Сервисы, которые создавали потребителя через старый конструктор, перестанут компилироваться — их нужно исправить (создавать `CommandFactory` и передавать).
- Тесты, которые создавали потребителя напрямую, перестанут компилироваться — их нужно либо исправить, либо временно `@Disabled` с пометкой, в какой задаче будет фикс.

**Проверка после шага:**
```bash
grep -rn "new ConsumerClass" src/ --include="*.java"
# Все вызовы должны использовать новый конструктор с CommandFactory
grep -rn "StaticFactory\.\|import.*StaticFactory" src/ --include="*.java"
# не должно быть вызовов (кроме самого статического класса)
```

### Шаг 5: Актуализировать тесты

1. **Тест доступности CLI** — если был тест, который искал исполняемый файл через жёсткие if-else по ОС:
   - Удалить метод с if-else и `FileNotFoundException`
   - Заменить на `CommandResolver` с fallback-путями из `agent-runner.properties`
   - Команду (`--version`) собирать через `CommandFactory.buildCommand()`

2. **Параметризованные тесты моделей** — используют `AgentRunnerFactory`, должны работать без изменений (фабрика уже передаёт CommandFactory).

3. **Интеграционные тесты** — используют сервис, который внутри создаёт раннер, должны работать без изменений.

### Шаг 6: Пометить старый класс как @Deprecated(forRemoval=true)

**Этот шаг — последний.** Выполняется ТОЛЬКО после того, как ни один класс в проекте не вызывает старый статический класс.

1. Добавить `@Deprecated(forRemoval=true)` и Javadoc с указанием замены.
2. Внутреннюю реализацию НЕ трогать — никакой делегации на новые классы.
3. Проверить, что `grep -r "OldClassName" src/ --include="*.java"` показывает только сам класс.

**Порядок выполнения:** `Шаг1 → Шаг2 → Шаг3 → Шаг4 → Шаг5 → Шаг6`

## Частые проблемы и решения

| Проблема | Решение |
|----------|---------|
| Тест падает, потому что команда нашлась в PATH | Использовать уникальное имя команды (например, `my-cli-test-123`) |
| После удаления старых конструкторов не компилируются тесты | `@Disabled` с пометкой "будет исправлено в TASK-006" |
| Сервис создаёт раннер через старый конструктор | Исправить сервис: создать CommandFactory через фабрику и передать в новый конструктор |
| Фабрика и сервис в разных пакетах | Сделать метод создания CommandFactory package-private или public |
| Дублируется логика создания CommandFactory в фабрике и сервисе | Использовать пакетный метод фабрики из сервиса |
