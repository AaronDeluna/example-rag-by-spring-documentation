# Преобразование плана рефакторинга в задачи

Используйте этот навык, когда нужно разбить многошаговый план рефакторинга архитектуры (описанный в plan.md или аналогичном документе) в структурированный список задач для последовательной реализации.

## Процесс

### 1. Прочитать исходный план
- Загрузить документ с планом рефакторинга/миграции (например, `plan.md`)
- Определить: что меняется, какие новые компоненты создаются, какие существующие модифицируются, что удаляется

### 2. Изучить текущую архитектуру проекта
- Прочитать ключевые файлы, которые будут затронуты (исходный код, тесты, конфигурацию)
- Понять существующие интерфейсы, иерархию классов, исключения, пакетную структуру
- Зафиксировать точки расширения (фабрики, enum'ы, properties)

### 3. Декомпозировать план на задачи
Каждая задача должна быть:
- **конкретной** — одно атомарное изменение (создать класс, модифицировать конструктор, добавить метод)
- **последовательной** — следующая задача может опираться на предыдущую
- **проверяемой** — можно однозначно сказать, выполнена она или нет

**Группировка по этапам (фазам):**

| Фаза | Что включает | Примеры |
|------|-------------|---------|
| **Новые компоненты** | Создание новых классов, интерфейсов, enum'ов, исключений | `OsType`, `CommandResolver`, `CommandNotFoundException` |
| **Конфигурация** | Добавление свойств, методов чтения конфигурации | Новые ключи в `.properties`, методы в `Properties`-классе |
| **Адаптация фабрик** | Изменение фабрик, внедрение зависимостей | `AgentRunnerFactory.createCommandFactory()` |
| **Модификация потребителей** | Изменение классов, использующих старый API | Конструкторы `QwenAgentRunner`/`QwenJudgeRunner` |
| **Деприкация старого API** | Пометка `@Deprecated`, делегирование на новое | `@Deprecated QwenCommandFactory` |
| **Адаптация тестов** | Обновление тестов под новую архитектуру | Замена жёстких путей на `CommandResolver` в тестах |
| **Верификация** | Сборка и прогон тестов | `mvn compile`, `mvn test -Dgroups=inner` |
| **Финальная очистка** | Удаление устаревших классов после перехода | Удалить `QwenCommandFactory` |

### 4. Сформулировать задачи
Каждая задача описывается по шаблону:
```
task_id: N
content: <глагол в повелительном наклонении> <что сделать> [в каком файле/пакете] [с какой целью]
status: pending
```

Примеры:
- «Создать пакет `org.mirent.skills.util.cli` с новыми компонентами: `OsType`, `CommandResolver`/`OsAwareCommandResolver`, `CommandFactory`/`QwenCommandFactoryImpl`»
- «Модифицировать `QwenAgentRunner`: заменить статические вызовы `QwenCommandFactory.buildCommand()` на `commandFactory.buildCommand()`, удалить старые конструкторы (без `CommandFactory`)»
- «Выполнить сборку проекта (`mvn compile`) и убедиться в отсутствии ошибок компиляции»

### 5. Разместить задачи

Есть два варианта размещения:

#### Вариант A: todo_write (для быстрых списков в процессе диалога)
Использовать `todo_write` для создания временного списка задач. Все задачи одного плана помещаются в единый список, отсортированный по порядку выполнения. Подходит для начального обсуждения и согласования.

#### Вариант B: Файлы задач в `.qwen/workplace/to_work/` (для формальной работы по правилам проекта)
Когда задачи согласованы и начинается реализация:

1. Для каждой задачи создать отдельный `.md`-файл по шаблону `task_template.md`
2. Имя файла: `TASK-<ID>_<код-модуля>_<краткое_описание>.md`
3. Поместить файл в `.qwen/workplace/to_work/`
4. Добавить запись в `.qwen/workplace/TASK_INDEX.md`
5. Установить статус `📋 Pending`

**Определение кода модуля:** прочитать `PROJECT_RULES.md` в `.qwen/workplace/`, найти соответствующий модулю код из таблицы. Если модуль не указан — добавить его (см. `setup-project-workplace`).

Структура файла задачи (по `task_template.md`):
- Информация о задаче (модуль, ID)
- Описание задачи
- Критерии приёмки (Acceptance Criteria)
- TDD Цикл (RED → GREEN → REFACTOR с чек-боксами)
- Работа с существующим кодом (characterization test при необходимости)
- Чек-лист завершения
- Статус (дата создания/начала/завершения, статус)

### 6. Корректировка задач после ревью (опционально)
Когда пользователь предоставляет обратную связь (например, в виде `plan2.md` с анализом задач или текстовыми замечаниями):

1. **Прочитать документ ревью** — выявить все рекомендации и замечания по каждой задаче
2. **Обновить файлы задач** — для каждой задачи:
   - Исправить описание, критерии приёмки, TDD-цикл согласно ревью
   - Добавить/убрать зависимости между задачами
   - Исправить порядок выполнения в заметках
   - Добавить новые чек-боксы или изменить существующие
3. **Перенумеровать при необходимости** — если порядок задач изменился, создать новые файлы и удалить старые:
   - Удалить старый файл из `to_work/`
   - Создать новый с правильным ID и именем
   - Обновить `TASK_INDEX.md`
4. **Типичные корректировки после ревью:**
   - Убрать обратную совместимость (старые конструкторы, legacy-делегацию)
   - Перенести деприкацию `@Deprecated(forRemoval=true)` в самый конец очереди
   - Добавить `RunnerLogWriter` или другие пропущенные зависимости в фабрику
   - Добавить адаптацию `AgentEvaluatorService` и других сервисов, создающих раннеры
   - Создать шаблон конфигурации в `src/main/resources/` (не только в тестовых ресурсах)
   - Добавить тесты для всех вариантов ОС (не только для Linux)

## Важные правила
- **Не ссылаться на исходный `plan.md`** в формулировках задач — задачи должны быть самодостаточными
- **Не сохранять обратную совместимость** — старый API помечается `@Deprecated(forRemoval=true)` без делегирования на новую реализацию. Весь код, использующий старый API, перерабатывается под новую архитектуру. Старые конструкторы/методы удаляются, а не дублируются через legacy-делегацию
- **Порядок: сначала переработка потребителей, потом деприкация** — сначала все классы, вызывающие старый API, переводятся на новый (TDD-цикл), и только потом старый API помечается `@Deprecated(forRemoval=true)`. Это гарантирует, что к моменту деприкации в проекте не осталось ссылок на устаревший код
- **Characterization tests — только для фиксации текущего поведения перед рефакторингом**, не для поддержки обратной совместимости
- **Верификация — обязательная фаза** — после внесения изменений должна быть задача на сборку и задачу на прогон тестов
- **Финальная очистка** — если класс помечен `@Deprecated(forRemoval=true)` и больше не используется нигде в проекте, он может быть удалён в отдельной финальной задаче
- **Пропущенные зависимости** — при адаптации фабрик и потребителей проверять ВСЕ места создания изменяемых классов (включая сервисы, которые создают раннеры внутри — например, `AgentEvaluatorService` создающий `QwenJudgeRunner`). Использовать `Find Usages` / `grep -r` для обнаружения всех мест
- **Конфигурация в main/resources** — новые .properties параметры добавлять не только в `src/test/resources/`, но и в `src/main/resources/` (шаблон с комментариями), чтобы приложение имело конфигурацию по умолчанию вне тестов
