## Обновлённые рекомендации с учётом выделения SDK

### Контекст

Код модуля `skills` планируется переработать в **отдельную SDK-библиотеку**, которая будет подключаться как зависимость в проекты, использующие автотесты для AI-агентов (Qwen, Claude и др.). Это накладывает дополнительные требования к архитектуре, API-дизайну, документированию и управлению версиями.

---

### 1. Абстрактный API без привязки к реализации (высший приоритет)

**Суть:** SDK должен предоставлять интерфейсы и абстрактные классы, а все конкретные реализации (парсеры, экстракторы, фабрики) должны быть подключаемы через конфигурацию или ServiceLoader.

**Ключевые интерфейсы для публичного API:**
- `AgentRunner` – основной контракт для запуска агента.
- `JudgeRunner` – для оценки результатов.
- `CommandFactory`, `CommandResolver` – для сборки команд.
- `LogParser<T>`, `ResultExtractor<T>`, `SkillCallExtractor<T>` – стратегии для обработки вывода.
- `AgentDefinition` – описание агента (имя, стратегии, команда).

**Принципы:**
- Все реализации должны быть в отдельных пакетах (например, `impl.qwen`, `impl.claude`), чтобы пользователь мог выбрать нужную.
- Публичное API не должно зависеть от конкретных DTO-классов, связанных с форматом какого-либо CLI.
- Предоставить **SPI (Service Provider Interface)**, чтобы пользователи могли подключать свои реализации стратегий без изменения кода SDK.

---

### 2. Конфигурация через файлы и переменные окружения

**Суть:** SDK должен поддерживать загрузку конфигурации из различных источников (properties, YAML, переменные окружения) с возможностью переопределения.

**Рекомендации:**
- Предоставить `AgentConfiguration` – объект, который можно построить из файла или программно.
- Поддерживать подстановку переменных (`${user.home}`, `${env.HOME}`), как уже реализовано.
- Сделать возможным указание активного агента через системное свойство (`agent.cli=QWEN`) или переменную окружения (`AGENT_CLI=CLAUDE`).
- Для тестов предусмотреть возможность передачи конфигурации напрямую в код (без файлов).

---

### 3. Модульность и расширяемость

**Суть:** SDK должен быть разбит на модули с чёткими границами, чтобы пользователи могли подключать только нужные части.

**Предлагаемая структура модулей:**
- **`sdk-core`** – интерфейсы, абстрактные классы, базовые исключения, утилиты.
- **`sdk-common`** – реализации для работы с командной строкой (CommandExecutor, OsAwareCommandResolver), общие DTO.
- **`sdk-qwen`** – стратегии для Qwen (парсер, экстракторы, фабрика команд).
- **`sdk-claude`** – стратегии для Claude (если планируется поддержка).
- **`sdk-test`** – вспомогательные классы для тестирования (матчеры, утилиты для создания WUT).

**Преимущества:**
- Пользователь подключает только те модули, которые нужны.
- Легко добавлять поддержку новых CLI, создавая новый модуль.
- Упрощается тестирование и поддержка.

---

### 4. Универсальные DTO с возможностью хранения сырых данных

**Суть:** DTO должны быть гибкими и не завязаны на конкретный CLI, но при этом сохранять возможность детального анализа при необходимости.

**Рекомендуемый DTO:**
```java
public class AgentResult {
    private final String stdout;
    private final String stderr;
    private final int exitCode;
    private final boolean timedOut;
    private final String finalResult;
    private final List<String> skillCalls;
    private final Map<String, Object> metadata; // например, steps, model, tokens
    private final Optional<Object> rawLog;      // опционально, для отладки
}
```
- `rawLog` хранится как `Object` – это может быть `List<JsonNode>` для Qwen, `List<Map>` для Claude и т.д.
- Пользователь может получить сырые данные и распарсить их самостоятельно, если нужно.

---

### 5. Чёткое документирование и примеры использования

**Суть:** Как SDK, библиотека должна быть хорошо документирована, чтобы пользователи могли быстро начать работу.

**Обязательные разделы документации:**
- **Quick Start** – пример подключения и запуска первого теста.
- **Конфигурация** – описание всех параметров, переменных окружения, файлов конфигурации.
- **Добавление нового CLI** – пошаговое руководство по созданию стратегий и подключению через SPI.
- **Модули и зависимости** – описание артефактов и их назначения.
- **Интерактивные сценарии** – описание, если поддерживаются.
- **Javadoc** на все публичные API-классы и методы.

---

### 6. Тестируемость SDK (Unit + Integration)

**Суть:** SDK должен поставляться с набором тестов, которые можно запускать как при разработке, так и для проверки совместимости с разными версиями CLI.

**Рекомендации:**
- В модуле `sdk-test` предоставить утилиты для создания временных рабочих областей (`WutPreparer`), матчеры (`AgentMatcher`), заглушки для раннеров.
- Документировать, как пользователь может писать свои тесты, используя эти утилиты.
- Предоставить примеры интеграционных тестов для каждого поддерживаемого CLI, но не включать их в основной артефакт (или вынести в отдельный модуль).

---

### 7. Управление зависимостями и версионирование

**Суть:** SDK должен быть независим от внешних библиотек, чтобы не создавать конфликтов в проектах пользователей.

**Рекомендации:**
- Минимизировать внешние зависимости: использовать только `slf4j-api`, `jackson` (для работы с JSON), `commons-exec` (для запуска процессов). Все зависимости должны быть с `compile` или `provided` по необходимости.
- Использовать семантическое версионирование (MAJOR.MINOR.PATCH) для управления обратной совместимостью.
- Публиковать артефакты в Maven Central.

---

### 8. Поддержка интерактивных сценариев (опционально)

**Суть:** Если в SDK будет добавлена поддержка диалоговых тестов, она должна быть реализована как отдельный модуль (`sdk-interactive`), не обязательный для основного использования.

**Архитектура:**
- `InteractiveAgentRunner` – реализует `AgentRunner`, управляет процессом через `stdin/stdout`.
- `InteractionStrategy` – определяет, как распознавать запросы и как отвечать.
- Пользователь может реализовать свою стратегию, имплементируя интерфейс.

**Рекомендация:** Добавить эту функциональность после стабилизации основного API, если будет запрос от пользователей.

---

### 9. Поддержка разных версий CLI-агентов

**Суть:** SDK должен позволять работать с разными версиями одного и того же CLI, если формат вывода меняется.

**Рекомендация:**
- В конфигурации предусмотреть параметр `agent.qwen.version` (или аналогичный) и в зависимости от него выбирать соответствующую стратегию (через фабрику версий).
- Или предоставить возможность указывать класс стратегии явно, чтобы пользователь мог переопределить, если стандартная стратегия не подходит.

---

### 10. Логирование и мониторинг

**Суть:** SDK должен предоставлять понятные логи (на уровне `INFO`, `DEBUG`), чтобы пользователь мог отслеживать процесс выполнения и диагностировать проблемы.

**Рекомендация:**
- Использовать `slf4j` для логирования.
- В документации указать, какие настройки логирования рекомендуется использовать.
- Предоставить возможность включать/отключать детальное логирование через конфигурацию.

---

### 11. Обработка ошибок и исключений

**Суть:** SDK должен бросать исключения, специфичные для SDK (наследники `AgentSdkException`), чтобы пользователь мог легко перехватывать и обрабатывать ошибки.

**Рекомендация:**
- Создать иерархию исключений: `AgentSdkException` → `CommandNotFoundException`, `ParsingException`, `TimeoutException`, `ConfigurationException`.
- В исключениях всегда указывать контекст (какой агент, какая команда, что пошло не так).
- Не использовать `RuntimeException` в публичных API (кроме случаев, когда это явно документировано).

---

### 12. Поставка примеров и шаблонов

**Суть:** Чтобы облегчить начало работы, SDK должен поставляться с примерами кода и шаблонами конфигурации.

**Предлагаемые артефакты:**
- Пример `agent-runner.properties` с комментариями.
- Пример простого теста с использованием SDK.
- Пример добавления нового CLI через SPI.

---

### Итоговый вывод

Переход к SDK требует **повышенного внимания к дизайну API, модульности и документированию**. Основные усилия должны быть направлены на:

1. **Создание абстрактного API**, который не зависит от конкретных реализаций.
2. **Модульную структуру**, позволяющую подключать только нужные части.
3. **Гибкую конфигурацию** через файлы, переменные окружения и программно.
4. **Чёткую документацию** с примерами, чтобы пользователи могли легко начать использовать SDK.
5. **Поддержку расширяемости** через SPI и фабрики.

Это позволит SDK стать универсальным инструментом для автоматизации тестирования AI-агентов, легко адаптируемым к новым CLI и сценариям.
